# Project Runner plugin: run a PCB CAM project on the machine

## Context
PCB CAM turns board files into CNC jobs. Running them is still a manual chain for every job: load the file, open Autoleveler, apply the map, change the bit, zero Z at X0 Y0, then press Start. Most scrapped boards come from a slip somewhere in that chain:
- the wrong bit for the file
- levelling forgotten, or applied twice
- Z zeroed at the wrong place
- a lost connection mid-job, with no idea where to resume

**Project Runner** is a separate plugin that runs a whole PCB CAM project with all of those steps built in. It follows the project goal in `AGENTS.md`: a novice opens the project file, clicks through the prompts, and gets a board.

What it does:
- Opens a PCB CAM project file (`.pcbcam.json`) and lists its CNC jobs. The user picks which jobs to run and in what order; the default is the project's own order.
- Runs each job through gSender's sender. The Runner does no streaming of its own.
- Adds a **bit change** step wherever the bit changes, and lets the user insert one between any two jobs. After every bit change it walks through **zeroing Z** at X0 Y0.
- Has Autoleveler's probing and levelling **built in, in the project's own context**. There's one height map per project, and the probe area comes from the job with the largest area by default (the user can pick a different reference job). The map is applied automatically to the jobs that need it.
- Tracks every job: pending, running, done, cancelled or failed, with times, the line reached and the bit used.
- **Resumes** after a lost connection or a power cut, and **detects when the machine coordinates may be wrong** and guides the user through restoring them.

**Autoleveler stays a standalone plugin, unchanged.** The Runner reuses its pure modules (`scan.js`, `leveling.js`) through a copy (see Code sharing). Nothing in the Runner depends on the Autoleveler plugin being installed.

## What gSender gives a plugin (verified in gSender 1.7 Edge's app.asar, 2026-10-22)
- **`machine.command(cmd, ...args)` can send any controller command.** The `plugin:command` path calls `controller.command(cmd, ...args)` with no allow-list. This includes:
  - `gcode:start [lineToStartFrom, zMax, safeHeight, spindleDelay]`, where start-from-line is built in: gSender rebuilds the feed, spindle and modal state from the skipped part and moves to safe height first.
  - `gcode:pause`, `gcode:resume`, `gcode:stop`, `feedhold`, `cyclestart`, `unlock`, `reset`, `homing`, and `gcode` (raw lines).
- **Job loading:** `gcode.loadToVisualizer(text, name)` loads a file the way a user opening it would.
- **Controller events:** every controller event except `serialport:read`/`write` is forwarded on the `controller` topic (`machine.addListener(name, cb)`). That covers `sender:status` (sent / received / total / finishTime), `workflow:state`, `controller:state`, `serialport:open`/`close`, `gcode:toolChange`, `sender:M0M1`, `startup` and errors. These events are small, so there's no need for the 28 KB redux reads.
- **Overlap with gSender's own features:** gSender has a disconnect "Resume" dialog (`disconnect:recovery`, in memory only) and M6 tool-change wizards that work within one file. The Runner avoids both: each job is its own file, so no M6 is involved, and its resume state is on disk.

## Design

### Plugin shape
- **One `visualizer-overlay` contribution ("Run")**, so it stays loaded on the Carve page for the whole job. A `tools-page` iframe is unloaded on navigation and would stop tracking the job.
- The panel is compact: a job list, the current step's prompt and its buttons, and a status line. There's no large DOM and no live SVG. Any board drawing is a small canvas.
- Manifest permissions:
  - `machine:read`, `machine:write`, `machine:query`, `machine:parse`
  - `visualizer:load`, `viewer:draw`
  - `workspace:read`, `storage`, `fileSystem`
  - topics `controller` and `workspace`

### Opening a project
- File → **Open project** (File System Access) reads `.pcbcam.json`, which contains `{ project, boardFiles, jobs }`.
- **G-code is regenerated by the Runner** from the project and board files, using the PCB CAM core (the output is deterministic, and the project file doesn't store live G-code).
- **"What you reviewed is what you run":**
  - PCB CAM writes a small `gcodeHash` per job into the project file when it generates the job.
  - The Runner hashes its own output. If the hashes differ, it says the job is out of date and asks the user to open the project in PCB CAM and regenerate. It never runs a job the user didn't review.
  - Frozen ("kept") jobs already carry their G-code and run as stored.
- **Job selection:** a checkbox list in project order, with each job's bit, operation types, estimated time and side. A default warning fires when cutout isn't last.

### Run plan
The Runner turns the selected jobs into a flat list of **steps**. These are plain data, persisted, and drive both the UI and the resume logic:

```
setup → [home] → set XY origin → bit change(V-bit) → zero Z → probe map → run iso-top
      → bit change(0.8 drill) → zero Z → run drill-0.8 → bit change(0.8 end mill) → zero Z → run cutout → done
```

- A **bit change** is inserted automatically wherever consecutive jobs use different tools, and the user can add one anywhere (for example, a fresh V-bit halfway through).
- Each step has a status (`pending | active | done | skipped | failed | cancelled`) and timestamps. Run steps also record the last acknowledged line, the planner blocks still queued (from `Bf:`), the number of lines, and the levelled-file hash.
- Prompts name the physical action and the bit: "Insert **Drill 0.8 mm**. Clip the probe to it, then click **Zero Z**."

### Bit change and Z zeroing (zero-at-origin workflow)
1. Spindle off (`M5`), raise to safe Z, and move to a change position (default: X0 Y0 at safe Z, which keeps the steps simple).
2. Prompt for the next bit. The user clicks when the bit is in.
3. **Zero Z:** move to X0 Y0, probe with `G38.2` (plate thickness 0, because the probe clip is on the bit and the copper is the plate), then a slow second probe, then `G10 L20 P1 Z0`, then retract.
   - XY is never touched.
   - This reuses Autoleveler's probing code and its safety checks (probe pin state before the move, maximum travel).
4. The height map stays valid, because it's relative to the copper at X0 Y0 (`zeroAt: 'origin'`).

### Built-in levelling
- **Reference job:** by default, the job with the largest XY bounds, which is usually the cutout or the outline-sized isolation job. The user can pick another job. The probe area is that job's bounds plus a margin, extended to cover X0 Y0.
- **Grid size:** points are chosen from the area, at about a 10 mm pitch with at least 3×3. Probe feed, depth and travel use Autoleveler's defaults.
- **When it probes:** once per project, after the first Zero Z and before the first job that needs the map. The map is saved in the run state, so it's never probed twice by mistake. Re-probe is an explicit button.
- **Which jobs get levelled:** by default, the jobs that cut at copper depth (isolation, clearing, and engraving-depth jobs). Drilling and cutout cut past the bottom of the board, so they don't need it; the user can override this per job. Each job is levelled **exactly once**: the Runner levels the regenerated original and never a levelled file.
- If a job runs past the map, it shows Autoleveler's coverage warnings, and Start is blocked when the job goes more than 1 mm outside the map.

### Running a job
- Load the levelled (or plain) G-code with `loadToVisualizer`, check that `sender:status.total` matches the line count, then **the user clicks Start**, which sends `gcode:start`. gSender's own Start/Pause/Stop buttons stay in sync with commands sent from the plugin (Phase 0).
- **A job is done when `workflow:state` goes from `running` to `idle` and the controller reports Idle** (gSender then shows "Job End Status: COMPLETE").
  - Not `finishTime > 0`: that is set when the last line is *acknowledged*, which happens when it enters the controller's 100-block planner. In the Phase 0 run that was about 20 s before the job actually ended.
- **Lines reached:** `received` in `sender:status` runs ahead of execution by up to the planner depth.
  - The planner depth varies by board, so read it from `$I` `[OPT:…,<blocks>,<rx bytes>]`. The user's replacement board has 35 blocks; the simulator and the old board had 100.
  - The line actually executing ≈ `received` − blocks still queued, where queued = planner size − the `Bf:` free count in the status report.
  - `Bf:` is only reported when `$10` includes the buffer bit (`$10=3` with machine positions). The user's board has `$10=1`. The Runner asks the user to confirm the change once, and otherwise falls back to "back to the start of the current pass".
  - Arcs (G2/G3) are split into many planner blocks, so this is approximate. The Runner always steps back to the start of the path (see Recovery).
- `sender:status` is only meaningful for a run started from line 1. After `gcode:start <line>`, gSender reported received = total from the first second. During a resumed run, the Runner tracks progress from controller state and the job's end instead.
- Persist the progress fields throttled to every 5 s, and also on pause, error and close events.

### Trusted coordinates
- **When the snapshot is taken:** on Set origin and on every Zero Z. The snapshot holds the WCO (from the status reports; `$#` is unreliable on the user's link), MPos and whether the machine was homed.
- **What marks coordinates as "unverified":**
  - an alarm, a hard-limit trip, or a soft reset while moving
  - a controller reboot (`startup` / a `[VER:]` banner)
  - `serialport:close`, a port reopen or a power loss
  - a WCO that differs from the snapshot
  - an MPos jump that doesn't match the commanded motion
- While unverified, **Start is blocked** until the user restores them (see Recovery).
- Limit switches on the user's Lunyee 3020 share one input per axis (or all axes), so the controller can't tell + from −.
  - **Homing still works.** grblHAL homes each axis in the `$23` direction, so a shared input is fine.
  - **After a hard-limit trip**, the Runner infers the likely end from the last commanded direction and position, and tells the user which way to jog off before unlocking.

### Recovery
- **Connection lost, machine still powered** (the most common case: bridge, USB or EMI):
  - The bridge feed-holds on client loss, and grblHAL keeps its position if it wasn't reset mid-move.
  - **What gSender does (Phase 0):**
    - It shows a "Port Disconnected" dialog whose Resume button only reconnects. Its "suggested line" was wrong: it said line 10 while the machine was holding at about line 34, with lines up to 130 already queued in the planner.
    - On reconnect it does **not** reset the controller. The machine stays in Hold with its planner blocks and position intact.
    - gSender then clears its job progress and **enables Start**, which would rerun the job from line 1 on top of the held blocks.
  - **So the Runner takes over after a reconnect:**
    - It blocks Start and Cycle Start.
    - It reads the status: Hold, queued blocks (`Bf:`), WCO.
    - It computes the line reached: last `received` before the drop minus the blocks still queued.
    - It soft-resets while holding. That's safe: no alarm, position kept, planner cleared.
    - If the WCO matches the snapshot, coordinates stay trusted.
  - **Resume from line N:**
    - N is the start of the path containing the line reached, so the cut never starts mid-segment.
    - The Runner runs `gcode:start N, zMax, safeHeight` on the *same* levelled file. Its hash proves the line numbers still match.
    - **Choose N where the tool is above the surface.** gSender's resume preamble raises to `zMax + safeHeight`, restores the spindle (`M3 S…`), rapids to the line's XY, then **rapids (`G0`) down to the line's Z**. Starting mid-cut would plunge a fragile V-bit into the copper at rapid speed. So N is the line that plunges into the path, which leaves the descent to the job's own feed-rate plunge.
- **Power loss, or a reset with lost position:**
  - **Homing enabled (`$22`):** home, restore the saved G54 (grblHAL keeps it in non-volatile storage, and the Runner checks it against the snapshot), re-zero Z at X0 Y0 because the bit may have shifted, then restart **from the start of the interrupted pass**. Re-cutting part of an isolation pass at the same depth does no harm.
  - **No homing:** a guided re-reference. Jog to X0 Y0 using the origin mark or the board corner (there's a zoomed reference picture of the origin on the board), confirm, set XY, zero Z, then restart from the start of the interrupted pass. The Runner says plainly that alignment is only as good as the visual check.
- Every recovery asks the user to check the bit first, because a broken bit is a common cause of the stop.
- On first use, if homing isn't enabled, the Runner offers short guidance on enabling homing on a machine with limit switches (`$22=1`, direction mask `$23`, pull-off `$27`). It never changes `$` settings without the user confirming each one.

### Persistence
- **Run state lives in a file on disk next to the project:** `<board>.pcbrun.json`. It holds the selected jobs, the steps and their statuses, the height map, the coordinate snapshots, `lastAckedLine` and history. It's written with the File System Access API, debounced, plus at every step boundary.
  - It's a separate file, so PCB CAM and the Runner never overwrite each other's saves.
- **Plugin storage** keeps only small pointers (the last run's name and current step). After a gSender restart the user reopens the run file; file handles don't survive a restart, because the origin changes.
- **History:** the run file keeps one entry per job attempt, with start, end, result, line reached, bit and notes ("bit broke"). The list is bounded to 200 entries.

### Code sharing
- Plugins are served separately, and there's no build step. Shared pure modules are **copied** into `plugins/project-runner/ui/vendor/`:
  - PCB CAM's `ui/core/` (generation)
  - Autoleveler's `scan.js` and `leveling.js`
  - A `scripts/sync-shared.mjs` script does the copying, and a test fails if a copy differs from its source.
- Runner-specific logic goes in pure modules with Node tests:
  - `plan.js` (steps from jobs, bit-change insertion, reference job choice)
  - `recovery.js` (coordinate-trust rules, resume line choice)
  - `runstate.js` (file schema, migrations)

### Changes to PCB CAM
- Move the job → G-code recipe into the core as one pure function, `generateJob(doc, jobId) → { ok, issues, files }`. Today it's spread over the UI (`runnable()`, `runJob()`, and the job name used as the project name), and the Runner must not keep a second copy of that logic.
- Write `gcodeHash` (and the core version) per job into the project file when a job is generated.
- Report jobs whose board files are missing from the project file. `Board.pcbcam.json` has a drilling operation but no drill file.
- Optionally, add a "Run in Project Runner" hint after Save.

## Phases
0. **Spikes:** done 2026-10-22; see Phase 0 findings below.
1. **Open project and run jobs:** open the file, pick jobs, steps, run through gSender, statuses, history, run file. *Built 2026-10-22:*
   - PCB CAM core: `generateJob(doc, jobId)` (`core/job.js`) is the one job → G-code recipe; PCB CAM's UI uses it and saves `gcodeHash` + `coreVersion` per job. Jobs whose board file is missing report `missing-file`.
   - Runner modules: `jobs.js` (open, regenerate, hash check; a file using several bits can't run), `plan.js` (selection, order, warnings, steps), `runstate.js` (run file, history ≤ 200), `tracker.js` (job end from workflow + sender + controller state), all with Node tests.
   - The run file embeds the project file, so a run continues from that one file after a restart. A step whose regenerated G-code no longer matches is blocked.
   - Each run step names its bit; Start needs the file loaded in gSender (line count checked), the machine Idle and connected, and a ticked "bit is in and Z is zeroed" box. Bit changes are prompts only until Phase 2.
   - After a failure or Stop, the step offers Run again (from line 1), Mark as done or Skip. Resume from a line is Phase 4.
2. **Bit change and Zero Z:** automatic bit-change insertion, manual insertion, a guided probe at X0 Y0. *Built 2026-10-22:*
   - Bit changes are steps of their own (`kind: 'bit'`) before every run step whose bit differs from the one before. The user can add one before any job not yet run ("Change bit", or `+⇄` in the list) and remove the ones they added. Run file version 2; version 1 files are migrated.
   - The step has two stages. **Change:** "Raise Z to" (`M5`, then `G90 G0 Z<height>` in work coordinates, i.e. above the copper; 20 mm by default, settable 1–50 mm next to the button and kept in plugin storage; it never moves down when Z is already higher, and Zero Z warns when Z is above the 25 mm the probe can reach) and swap the bit. **Zero Z** (`zeroz.js`, pure, with Node tests): probe input must be open, touch test with a screwdriver, `G0 X0 Y0` at the current height, `G38.2` down at most 25 mm at 60 mm/min, back off 0.5 mm, a second probe at 15 mm/min, `G10 L20 P0 Z0`, wait until the status reads work Z 0, then up 5 mm. Probe parsing comes from a synced copy of Autoleveler's `leveling.js`.
   - Every motion is a click, needs the machine connected, Idle and with no job open, sets gSender busy, and has a Stop (feed hold, then reset). An alarm or a lost connection stops it.
   - A job after a done bit change starts without the "bit is in" checkbox and reminds the user to take the probe clip off. The checkbox comes back when the bit change was skipped or the job's last attempt failed (an alarm may have moved Z), until a new bit change is done.
   - Not built: the bit change doesn't move XY to a change position (the probe moves to X0 Y0 anyway), and Raise Z doesn't know how much room is left above (it's a short, repeatable move).
2b. **Wizard UI and added steps:** *Built 2026-10-23:*
   - The panel is a wizard: a welcome page explains the three steps, then **1 Pick jobs** (ticked in project order, with a status badge and the reason a job can't run), **2 Order** (drag and drop, with ▲▼ as a fallback), **3 Run** (the step cards from Phases 1–2). A step bar shows where you are; setup steps can be revisited, and from the Run page too until anything has happened on the machine (`runStarted`: a step finished or running, or a bit change past the swap). Going back keeps the picks, order and added steps, and Start run writes the same run file again. After that the steps show as locked, and clicking them says why and what to do instead (skip a step, add a bit change, or close the run and start a new one).
   - On the Order page the user can add steps **before or after** any job (`commands.js`): a **bit change + zero Z** (it sets up the bit of the next job and replaces the automatic one there), a **pause with a message** (Done to continue), or **G-code** (up to 20 lines, sent on a click with Stop; M0/M1/M2/M30, M6, G38, G10/G92, G91, `$` settings and realtime characters are refused, with the step to use instead). Automatic bit changes are recomputed whenever the order changes.
   - **Restart** (Run page footer, once the run has started, not while anything runs): a confirm card warns that progress resets and done jobs are cut again, and to home and check X0 Y0 if position was lost. `restartRun` rebuilds the steps from the same jobs, order and added steps; history is kept with a "Run restarted" entry, and setup can be changed again until something runs.
   - **Set X0 Y0 is the first step of every run** (also after Restart): jog the bit tip to the board's front-left corner with gSender's jog controls (the card shows live work X/Y), then **Set X0 Y0 here** sends `G10 L20 P0 X0 Y0` and waits until the status reads 0,0. Z is untouched. "X0 Y0 is already set" skips it. Run file version 4 adds the `origin` step kind.
   - Run file version 3: step kinds `note` and `gcode`, and `commands` saved with the selection. Version 2 files open unchanged.
   - *Checked in real gSender against the simulator, 2026-10-23:* a full 9-step run of the user's Board project (Set X0 Y0, three bit changes with Zero Z, three jobs, a pause, a G-code step), then Restart, back to setup, Start run on the same file, and a panel reload that reopened the run. Zero Z stops cleanly on a limit alarm, on Stop and on a lost connection. Heap after GC 36.8 MB, as before the run. Fixed: Zero Z and Start were allowed while gSender had no machine state yet (now "Waiting for the machine to report its state."). The simulator now answers G4/G38.x only when done and keeps `$` lines in order, as Grbl does; it has `/probe?ms=` for the touch test.
   - Found, not fixed: all jobs are ticked by default, including duplicates such as `…_iso_cnc_1`. A "probe failed" message for ALARM:1 (a limit) still says to check the clip. If the connection drops mid-probe with the bridge's feed hold, Grbl answers nothing until a reset, so gSender can't reconnect (Phase 4).
3. **Built-in levelling:** *Built 2026-10-23* (`level.js`, pure, with Node tests; Autoleveler's `scan.js` is now synced too):
   - **What is levelled:** each G-code file whose operations include isolation or clearing (decided per file, so a split job's cutout file isn't). Drilling and cutout run as generated. There's no per-job switch (decided with the user).
   - **Probe area:** the cuts of the levelled files (not the largest job: the cutout runs outside the board, where there may be no copper), plus 1 mm, stretched to include X0 Y0. The low sides never go past 0 or past the cuts, because X0 Y0 is the board's corner. Grid about 10 mm apart, 3 to 12 points per axis.
   - **The probe step** (`kind: 'probe'`, run file version 5, map in `run.map`) comes once, right after the bit change for the first levelled job and before anything the user added there. It uses Autoleveler's scan with its defaults, but leaves work Z0 where Zero Z put it (`zeroFirst: false`); the map is applied relative to X0 Y0 (`zeroAt: 'origin'`), so later Zero Z steps keep it valid. The touch test is skipped only when Zero Z touched the copper with the same clip in the step before (within 15 min). Stop keeps the points so far: **Continue probing** checks the first point again and does the rest, **Start over** throws them away. **Skip levelling** runs the jobs as generated, and their cards say so.
   - **Running:** a levelled job loads as `<file>_leveled.nc`, levelled from the regenerated original (never twice). Load and Start are refused when a job runs more than 1 mm past the map, or when X0 Y0 moved more than 0.05 mm since probing (machine minus work position, saved with the map); the card offers **Probe again**. Progress and history count the levelled file's lines.
   - **Restart keeps the map** (decided with the user); the X0 Y0 check catches a board set up in a different place. A kept probe step doesn't lock setup. **Probe again** on a levelled job's card drops the map.
   - *Checked in the mock host:* probe after Zero Z, a levelled job run to the end, Restart with the map kept, X0 Y0 moved (refused, then Probe again), Stop mid-probe and Continue. *Checked in real gSender (2026-10-24):* a full run against the simulator (Set X0 Y0, Zero Z, 30-point probe, levelled job to the end, next bit change), and the user milled a real board with it on the Grbl 1.1f 3020.
4. **Coordinate trust and resume after a lost connection.**
5. **Power-loss recovery:** homing path and visual re-reference path, plus homing setup guidance.
6. **Release:** README, packaging, a real-app memory check (a heap that stays flat for a full job with usage data collection on).

## Phase 0 findings (2026-10-22, gSender 1.7.0-Edge-2)
How the spikes were run:
- gSender was connected over its network option to `scripts/grblhal-sim.mjs` on 127.0.0.1:2323. It's a grblHAL simulator with a 100-block planner, probing, work offsets, and fault injection over HTTP: disconnect, disconnect with feed hold, reset, power cycle, limit trip.
- The plugin side ran inside the Autoleveler overlay iframe (same SDK and permissions a Runner needs), driven from outside over CDP.
- The user's machine was offline (dead controller board), so nothing touched real hardware.

| Question | Result | Consequence |
|---|---|---|
| Load and start from an overlay plugin | `gcode.loadToVisualizer` enables gSender's Start. `machine.command('gcode:start')`, `'gcode:pause'` and `'gcode:resume'` work, and gSender's Start/Pause/Stop buttons and status header follow. | The Runner drives jobs through gSender's sender. No own streaming. |
| Start from line | `machine.command('gcode:start', 200, zMax, safeHeight)` resumed at line 200 (`job:start` reports `true`). The preamble rapids down to the line's Z (`G0`). During a resumed run, `sender:status` showed received = total at once. | Resume at a path's plunge line. Track resumed runs from controller state and job end, not `sender:status`. |
| Events while on another page | The overlay iframe stays mounted (same window object, hidden) on other pages, and controller events keep arriving. | A `visualizer-overlay` contribution is the right shape. |
| Job end | `finishTime` is set when the last line is acknowledged, about 20 s before the job ended. The end is `workflow:state` `idle` plus controller Idle. | Use the workflow and controller state for "done". |
| Lines reached | Grbl acknowledges a line when it enters the planner, so `received` leads execution by up to 100 blocks. | Line reached = received − queued blocks (`Bf:`), then back to the path start. |
| gSender's disconnect dialog | "Port Disconnected" with Resume (reconnect only). Suggested line 10 when the machine was at about line 34. | The Runner computes its own resume line and tells the user to ignore gSender's. |
| Reconnect behaviour | No soft reset on connect (`$I`, `$$`, `$E…`, `$#`, then `$G` every 0.5 s). The machine stayed in Hold with 100 blocks queued. gSender reset its progress and enabled Start. | The Runner blocks Start, soft-resets while holding, then resumes from its own line. |
| Controller events | `controller:state` carries the status; WCO arrives only every few reports and can be stale right after `G10`. | Take coordinate snapshots from a fresh report (or `$#` where it works). |
| Regenerating G-code | All 10 jobs in the user's two project files give identical SHA-256 in Node and in gSender's Electron engine, and across runs. | Regenerate in the Runner and check `gcodeHash`. |
| Missing inputs | `Board.pcbcam.json` has a drilling op without its drill file (job fails with `no-operations`). | The Runner lists such jobs as not runnable, with the reason. |
| The user's machine (replacement board, read 2026-10-22) | Plain **Grbl 1.1f** ("Monport" build), not grblHAL. `[OPT:VMZHL,35,254]`: 35 planner blocks, 254-byte receive buffer. **Homing on** (`$22=1`, `$23=3`: X and Y home toward minus, Z up), hard limits on (`$21=1`), soft limits off. `$130–132` are 500/500/200 (not the 3020's travel). `$10=1` (no `Bf:`). The board starts **Idle and unlocked** after a reset despite the `L` (lock until homed) option. | Power-loss recovery can home, then restore G54. A controller restart must still mark coordinates untrusted, because the board doesn't lock itself. The planner and receive-buffer sizes come from `$I`, never hard-coded. |

## Verification
- **Unit tests:**
  - step planning (bit-change insertion, reference job choice)
  - recovery decisions for each trigger
  - resume line selection (snapping back to the start of a path)
  - hash check
  - run file round-trip
  - vendored copies identical to their sources
- **Real gSender against `scripts/grblhal-sim.mjs`:** a full run with injected disconnect (with and without feed hold), soft reset, limit trip and power cycle.
- **Mock host (`npm run dev`):** UI work without gSender.
- **Real machine:**
  - a dry run with Z raised: every step, a deliberate bridge disconnect, then resume
  - then a real board: isolation, drill and cutout with three bit changes
