# Project Runner plugin: run a PCB CAM project on the machine

## Context
PCB CAM turns board files into CNC jobs. Running them is still a manual chain for every job: load the file, open Autoleveler, apply the map, change the bit, zero Z at X0 Y0, then press Start. Most scrapped boards come from a slip somewhere in that chain:
- the wrong bit for the file
- levelling forgotten, or applied twice
- Z zeroed at the wrong place
- a lost connection mid-job, with no idea where to resume

**Project Runner** is a separate plugin that runs a whole PCB CAM project with all of those steps built in. It follows the project goal in `AGENTS.md`: a novice opens the project file, clicks through the prompts, and gets a board.

What it does:
- Opens a PCB CAM project file (`.pcbcam.json`) and lists its CNC jobs. The user picks which jobs to run and in what order; the default is the project's own order.
- Runs each job through gSender's sender. The Runner does no streaming of its own.
- Adds a **bit change** step wherever the bit changes, and lets the user insert one between any two jobs. After every bit change it walks through **zeroing Z** at X0 Y0.
- Has Autoleveler's probing and levelling **built in, in the project's own context**. There's one height map per project, and the probe area comes from the job with the largest area by default (the user can pick a different reference job). The map is applied automatically to the jobs that need it.
- Tracks every job: pending, running, done, cancelled or failed, with times, the line reached and the bit used.
- **Resumes** after a lost connection or a power cut, and **detects when the machine coordinates may be wrong** and guides the user through restoring them.

**Autoleveler stays a standalone plugin, unchanged.** The Runner reuses its pure modules (`scan.js`, `leveling.js`) through a copy (see Code sharing). Nothing in the Runner depends on the Autoleveler plugin being installed.

## What gSender gives a plugin (verified in gSender 1.7 Edge's app.asar, 2026-10-22)
- **`machine.command(cmd, ...args)` can send any controller command.** The `plugin:command` path calls `controller.command(cmd, ...args)` with no allow-list. This includes:
  - `gcode:start [lineToStartFrom, zMax, safeHeight, spindleDelay]`, where start-from-line is built in: gSender rebuilds the feed, spindle and modal state from the skipped part and moves to safe height first.
  - `gcode:pause`, `gcode:resume`, `gcode:stop`, `feedhold`, `cyclestart`, `unlock`, `reset`, `homing`, and `gcode` (raw lines).
- **Job loading:** `gcode.loadToVisualizer(text, name)` loads a file the way a user opening it would.
- **Controller events:** every controller event except `serialport:read`/`write` is forwarded on the `controller` topic (`machine.addListener(name, cb)`). That covers `sender:status` (sent / received / total / finishTime), `workflow:state`, `controller:state`, `serialport:open`/`close`, `gcode:toolChange`, `sender:M0M1`, `startup` and errors. These events are small, so there's no need for the 28 KB redux reads.
- **Overlap with gSender's own features:** gSender has a disconnect "Resume" dialog (`disconnect:recovery`, in memory only) and M6 tool-change wizards that work within one file. The Runner avoids both: each job is its own file, so no M6 is involved, and its resume state is on disk.

## Design

### Plugin shape
- **One `visualizer-overlay` contribution ("Run")**, so it stays loaded on the Carve page for the whole job. A `tools-page` iframe is unloaded on navigation and would stop tracking the job.
- The panel is compact: a job list, the current step's prompt and its buttons, and a status line. There's no large DOM and no live SVG. Any board drawing is a small canvas.
- Manifest permissions:
  - `machine:read`, `machine:write`, `machine:query`, `machine:parse`
  - `visualizer:load`, `viewer:draw`
  - `workspace:read`, `storage`, `fileSystem`
  - topics `controller` and `workspace`

### Opening a project
- File → **Open project** (File System Access) reads `.pcbcam.json`, which contains `{ project, boardFiles, jobs }`.
- **G-code is regenerated by the Runner** from the project and board files, using the PCB CAM core (the output is deterministic, and the project file doesn't store live G-code).
- **"What you reviewed is what you run":**
  - PCB CAM writes a small `gcodeHash` per job into the project file when it generates the job.
  - The Runner hashes its own output. If the hashes differ, it says the job is out of date and asks the user to open the project in PCB CAM and regenerate. It never runs a job the user didn't review.
  - Frozen ("kept") jobs already carry their G-code and run as stored.
- **Job selection:** a checkbox list in project order, with each job's bit, operation types, estimated time and side. A default warning fires when cutout isn't last.

### Run plan
The Runner turns the selected jobs into a flat list of **steps**. These are plain data, persisted, and drive both the UI and the resume logic:

```
setup → [home] → set XY origin → bit change(V-bit) → zero Z → probe map → run iso-top
      → bit change(0.8 drill) → zero Z → run drill-0.8 → bit change(0.8 end mill) → zero Z → run cutout → done
```

- A **bit change** is inserted automatically wherever consecutive jobs use different tools, and the user can add one anywhere (for example, a fresh V-bit halfway through).
- Each step has a status (`pending | active | done | skipped | failed | cancelled`) and timestamps. Run steps also record `lastAckedLine`, the number of lines, and the levelled-file hash.
- Prompts name the physical action and the bit: "Insert **Drill 0.8 mm**. Clip the probe to it, then click **Zero Z**."

### Bit change and Z zeroing (zero-at-origin workflow)
1. Spindle off (`M5`), raise to safe Z, and move to a change position (default: X0 Y0 at safe Z, which keeps the steps simple).
2. Prompt for the next bit. The user clicks when the bit is in.
3. **Zero Z:** move to X0 Y0, probe with `G38.2` (plate thickness 0, because the probe clip is on the bit and the copper is the plate), then a slow second probe, then `G10 L20 P1 Z0`, then retract.
   - XY is never touched.
   - This reuses Autoleveler's probing code and its safety checks (probe pin state before the move, maximum travel).
4. The height map stays valid, because it's relative to the copper at X0 Y0 (`zeroAt: 'origin'`).

### Built-in levelling
- **Reference job:** by default, the job with the largest XY bounds, which is usually the cutout or the outline-sized isolation job. The user can pick another job. The probe area is that job's bounds plus a margin, extended to cover X0 Y0.
- **Grid size:** points are chosen from the area, at about a 10 mm pitch with at least 3×3. Probe feed, depth and travel use Autoleveler's defaults.
- **When it probes:** once per project, after the first Zero Z and before the first job that needs the map. The map is saved in the run state, so it's never probed twice by mistake. Re-probe is an explicit button.
- **Which jobs get levelled:** by default, the jobs that cut at copper depth (isolation, clearing, and engraving-depth jobs). Drilling and cutout cut past the bottom of the board, so they don't need it; the user can override this per job. Each job is levelled **exactly once**: the Runner levels the regenerated original and never a levelled file.
- If a job runs past the map, it shows Autoleveler's coverage warnings, and Start is blocked when the job goes more than 1 mm outside the map.

### Running a job
- Load the levelled (or plain) G-code with `loadToVisualizer`, check that `sender:status.total` matches the line count, then **the user clicks Start**, which sends `gcode:start`.
- Track progress from `sender:status` and `workflow:state`. A job is done when `finishTime > 0` and every line has been received.
  - gSender's own finish rule still applies: every line acked and the machine Idle for 500 ms.
- Persist `lastAckedLine` throttled to every 5 s, and also on pause, error and close events.

### Trusted coordinates
- **When the snapshot is taken:** on Set origin and on every Zero Z. The snapshot holds the WCO (from the status reports; `$#` is unreliable on the user's link), MPos and whether the machine was homed.
- **What marks coordinates as "unverified":**
  - an alarm, a hard-limit trip, or a soft reset while moving
  - a controller reboot (`startup` / a `[VER:]` banner)
  - `serialport:close`, a port reopen or a power loss
  - a WCO that differs from the snapshot
  - an MPos jump that doesn't match the commanded motion
- While unverified, **Start is blocked** until the user restores them (see Recovery).
- Limit switches on the user's Lunyee 3020 share one input per axis (or all axes), so the controller can't tell + from −.
  - **Homing still works.** grblHAL homes each axis in the `$23` direction, so a shared input is fine.
  - **After a hard-limit trip**, the Runner infers the likely end from the last commanded direction and position, and tells the user which way to jog off before unlocking.

### Recovery
- **Connection lost, machine still powered** (the most common case: bridge, USB or EMI):
  - The bridge feed-holds on client loss, and grblHAL keeps its position if it wasn't reset mid-move.
  - On reconnect, read the status: if the WCO matches the snapshot and no alarm or reset happened, coordinates stay trusted.
  - Offer **Resume from line N** (`lastAckedLine` minus a small backoff, rounded back to the start of the current path so the cut doesn't start mid-segment). This runs `gcode:start N` on the *same* levelled file, and the hash check proves the line numbers still match.
- **Power loss, or a reset with lost position:**
  - **Homing enabled (`$22`):** home, restore the saved G54 (grblHAL keeps it in non-volatile storage, and the Runner checks it against the snapshot), re-zero Z at X0 Y0 because the bit may have shifted, then restart **from the start of the interrupted pass**. Re-cutting part of an isolation pass at the same depth does no harm.
  - **No homing:** a guided re-reference. Jog to X0 Y0 using the origin mark or the board corner (there's a zoomed reference picture of the origin on the board), confirm, set XY, zero Z, then restart from the start of the interrupted pass. The Runner says plainly that alignment is only as good as the visual check.
- Every recovery asks the user to check the bit first, because a broken bit is a common cause of the stop.
- On first use, if homing isn't enabled, the Runner offers short guidance on enabling homing on a machine with limit switches (`$22=1`, direction mask `$23`, pull-off `$27`). It never changes `$` settings without the user confirming each one.

### Persistence
- **Run state lives in a file on disk next to the project:** `<board>.pcbrun.json`. It holds the selected jobs, the steps and their statuses, the height map, the coordinate snapshots, `lastAckedLine` and history. It's written with the File System Access API, debounced, plus at every step boundary.
  - It's a separate file, so PCB CAM and the Runner never overwrite each other's saves.
- **Plugin storage** keeps only small pointers (the last run's name and current step). After a gSender restart the user reopens the run file; file handles don't survive a restart, because the origin changes.
- **History:** the run file keeps one entry per job attempt, with start, end, result, line reached, bit and notes ("bit broke"). The list is bounded to 200 entries.

### Code sharing
- Plugins are served separately, and there's no build step. Shared pure modules are **copied** into `plugins/project-runner/ui/vendor/`:
  - PCB CAM's `ui/core/` (generation)
  - Autoleveler's `scan.js` and `leveling.js`
  - A `scripts/sync-shared.mjs` script does the copying, and a test fails if a copy differs from its source.
- Runner-specific logic goes in pure modules with Node tests:
  - `plan.js` (steps from jobs, bit-change insertion, reference job choice)
  - `recovery.js` (coordinate-trust rules, resume line choice)
  - `runstate.js` (file schema, migrations)

### Changes to PCB CAM
- Write `gcodeHash` (and the core version) per job into the project file when a job is generated.
- Optionally, add a "Run in Project Runner" hint after Save.

## Phases
0. **Spikes:**
   - Load and start a job from an overlay plugin. Do gSender's Start/Pause buttons stay in sync? Does start-from-line work through `machine.command`?
   - Does `sender:status` keep arriving while the user is on another page?
   - Does gSender's own disconnect "Resume" dialog compete with the Runner, and which one should handle it?
   - What does the user's machine report for `$22`/`$23`?
   - Does regenerating from a project file reproduce PCB CAM's G-code byte for byte?
1. **Open project and run jobs:** open the file, pick jobs, steps, run through gSender, statuses, history, run file.
2. **Bit change and Zero Z:** automatic bit-change insertion, manual insertion, a guided probe at X0 Y0.
3. **Built-in levelling:** reference job (largest area, or chosen), automatic grid, one map per project, levelling each job exactly once, coverage gate.
4. **Coordinate trust and resume after a lost connection.**
5. **Power-loss recovery:** homing path and visual re-reference path, plus homing setup guidance.
6. **Release:** README, packaging, a real-app memory check (a heap that stays flat for a full job with usage data collection on).

## Verification
- **Unit tests:**
  - step planning (bit-change insertion, reference job choice)
  - recovery decisions for each trigger
  - resume line selection (snapping back to the start of a path)
  - hash check
  - run file round-trip
  - vendored copies identical to their sources
- **Mock host (`npm run dev`):** a full run with a simulated disconnect and a simulated reset, using the simulated Grbl.
- **Real machine:**
  - a dry run with Z raised: every step, a deliberate bridge disconnect, then resume
  - then a real board: isolation, drill and cutout with three bit changes
